## 남은 발견 사항

### R3-01 · P2 · 모듈 기준선 검사는 여전히 기본 120초로 시작한다

**근거:** `logs/probe/mutation_tasks.py:185–193`와 `214–220`, `245–250`; v2 diff:839–863.

단일 변이와 hard 결합 검사에는 `min(120, remaining)`이 전달된다. 반면 각 모듈의 최초 정상 기준선은 `_run_unittest(project, Path(test).name)` 그대로다. 전체 시간이 1초 남은 시점에 다음 모듈에 진입하면 그 기준선은 최대 120초 제한으로 시작할 수 있다. 시작 전 `elapsed > max_seconds` 검사만으로는 막지 못한다.

**후속 보완:** 기준선에도 같은 남은 시간 정책을 적용한다. 남은 시간이 너무 작으면 새 검사를 시작하지 않고 중간 결과와 종료 이유를 보존한다. 프로세스 종료·임시 파일 정리 시간은 별도 여유로 취급한다.

**후속 검사 명세:** 가짜 시계/runner로 다음 모듈에 진입할 때 1초만 남은 경우, 기준선 호출을 생략하거나 그 제한을 넘기지 않는지 확인한다. 추가된 `test_a_bounded_run_honours_a_shorter_limit`는 runner가 전달받은 제한을 지키는지 검사하며, 이 호출부가 제한을 빠뜨리지 않았는지는 확인하지 않는다. 이번 검토에서 실행하지 않았다.

### R3-02 · P2 · 이미 배운 auto에 나중에 추가된 최종 검사 결과는 다시 반영되지 않는다

**근거:** `jarvis/developer.py:1008–1025`, `jarvis/insights.py:193–201`; v2 diff:205–226, 420–429, 674–675.

사후 증거를 정확히 묶는 함수는 개선됐지만, 학습 완료 키는 여전히 `run_id@auto.at`뿐이다. 다음 순서에서 최신 전체 검사 결과가 교훈 입력에 들어가지 않는다.

1. auto가 복사본의 선택 검사를 통과하고 승인 대기 상태가 된다.
2. 사용자가 `/dev-learn`을 실행해 유효 교훈 연산을 저장한다. 이 auto의 키가 learned에 들어간다.
3. 이후 같은 후보를 적용하고 전체 검사에서 FAIL이 기록된다.
4. 다시 `/dev-learn`을 실행해도 auto의 시각/키는 같으므로 fresh에서 제외된다. 스크립트의 `unlearned`도 같은 방식이다.

현재 일괄 평가처럼 모든 검사가 끝난 뒤 한 번 추출하는 경우에는 이 순서가 발생하지 않는다. 대화형 개발에서 검사 전후에 학습 명령을 쓰거나, 아직 완료되지 않은 JSONL을 추출한 뒤 다시 읽는 경우의 문제다. 이 검토로 현재 교훈의 특정 오류 원인이 확정되는 것은 아니다.

**후속 설계:** 동일 증거의 중복 학습 방지는 유지하면서, 처리 키에 사후 증거 버전/지문을 별도로 관리하거나 최종 검사 대기 기록을 미완료로 남긴다. 증거가 추가됐을 때는 이전 교훈을 재검토할 수 있어야 한다. 단순히 learned를 지워 모든 기록에 재투표하면 R2-05가 다시 생기므로, 기존 근거를 갱신하는 절차와 같은 근거의 반복 투표를 구분한다.

**후속 검사 명세:** auto → learn → apply → suite FAIL → learn 순서에서 새 실패 근거가 전달되고, 그 뒤 동일 입력 재시도에는 점수가 중복 증가하지 않는지 가짜 생성기로 확인한다. 새 모델 실행이 필요하지 않은 검사로 만들 수 있다. 이번에는 명세만 남겼다.

### R3-03 · P2 · manifest의 일부 필드는 실제 실행값이 아닌 설정 원시값이다

**근거:** `logs/probe/coding_agent_eval.py:116–121`; `jarvis/app.py::effective_runtime_limits`, `clamp_output_budget`, `num_gpu_for`.

- `num_ctx`는 desktop/global 두 설정값만 기록한다. 둘 다 자동값 0이면 manifest에는 0이 남지만 실행은 하드웨어 프로필 기본 문맥 크기를 사용한다.
- `max_output_tokens`에는 설정값을 기록하며, 실제 provider에 전달되는 문맥 예산 제한 후 num_predict와 다를 수 있다.
- `num_gpu`에는 CLI 인자만 기록한다. CLI가 0일 때는 평가 settings에서 기존 `num_gpu_layers`와 모델 범위 설정을 유지하므로 실제 선택된 값과 달라질 수 있다.

현재 명시적 27B/GPU54 실행에서 위 차이가 실제 발생했다고 관측한 것은 아니다. manifest를 다른 하드웨어·기본 옵션 실행에서도 재현 근거로 쓰려면 구분해야 한다.

**후속 보완:** requested와 effective 값을 나누고, 이미 만든 core/provider의 실제 문맥·출력·GPU 층 옵션과 하드웨어 프로필을 기록한다. 모델/서버에서 실제로 반영했는지 확인하지 못한 값은 요청값임을 표시한다. 현재 manifest에는 에이전트 코드 별도 지문, 설정 전체의 재현 가능한 비밀값 제외 지문, 서버 KV 조건, 모델 파일 버전까지 포함된 것은 아니므로 ‘실행 조건 전체’가 완전히 보존됐다고 표현하지 않는다.
