# ALEX 코딩 에이전트 개선 검토 — 2026-10-03 Codex

## 조사 범위와 협업 보호

사용자 요청: 코딩 에이전트 능력을 Sonnet 5 수준까지 높일 방안을 현재 코드에서 찾기. Claude의 작업을 방해하지 않도록 먼저 실행 프로세스·최신 인계·파일 시각을 확인했다. 23:10부터 Claude의 전체 검증이 실행 중이었고, 23:15 인계에서 완료(907 tests, 3 skipped, release PASS)와 23:13 재시작을 확인했다. 코딩 코드·설정·기존 평가 스크립트·평가 결과는 변경하지 않았다. GPU 평가와 모델 로드도 실행하지 않았다.

## 현재 구현과 성능 증거

- 코딩용 문맥/글자 예산/GPU 층 설정과 `JarvisCore.coding_runtime`은 ADR-076에서 구현됐다. 기본 설정은 기존 동작을 유지한다. 새 설정에서의 실제 성능 향상은 아직 측정하지 않았다.
- 독립 풀이 횟수 `coding_auto_attempts`는 ADR-077에서 구현됐다. 기본 1, 최대 5. 실패한 풀이를 원본 상태로 되돌려 새로 시도하며 지정 테스트가 처음 통과하면 멈춘다. 여러 후보를 모두 전체 검사하고 가장 작은 것을 고르는 기능과는 동작이 다르다.
- workspace 제한, 파일 검색/읽기, SEARCH/REPLACE 수정안, 원본 백업/승인/rollback, 선택 테스트의 지문 고정, 결과 기록, 선택적 API 요약이 이미 있다. 모델이 수정 도중 탐색 도구를 직접 여러 차례 호출하는 루프는 아직 연결되지 않았다.
- 완료된 예전 변이 과제에서 쉬운 15/16, 어려운 9/11이 엄격 통과했다. 어려운 과제의 지정 테스트 통과는 10개였지만 전체 검사 통과는 9개였다. 기존 교훈 on/off의 성공 집합은 같았다. 작은 변이 과제·옛 소스/설정 조건이므로 범용 코딩 능력이나 현재 새 코드의 품질을 뜻하지 않는다.
- `core.py` 과제에서는 모델이 존재하지 않는 `read()`/`read_file()`를 반복하고 실제 `run(path=...)`를 찾지 못했다. API 요약이 그 실패 한 건을 해결한 관측은 있으나, 일반 성능 향상으로 확정할 표본은 아니다.

## 먼저 구현·검증할 순서

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 실제 과거 버그/기능 과제를 고정한 기준선 | 고치기 전 실패·고친 뒤 통과를 확인한 15개 이상으로 시작하고, 보지 못한 다중 파일 과제로 확대한다. 입력 소스·테스트·설정·모델·시간 예산을 기록한다. |
| 2 | 위치 찾기 → 수정과 모델의 반복 탐색 | 기존 검색·범위 읽기·시그니처/사용처 조회를 격리 복사본 안에서 호출할 수 있게 연결한다. API/의존성 과제의 성공률이 같은 시간 예산에서 증가해야 한다. |
| 3 | 문맥 크기와 실제 제공 문맥을 함께 조정 | 토큰 수와 잘린 파일 범위를 기록한다. 64K 설정만으로 필요한 코드가 전부 들어갔다고 단정하지 않는다. |
| 4 | 성공 수정안 선택 전에 전체 회귀 검사 | 지정 테스트 통과와 전체 통과를 구분하고, 고정 기준선 대비 새 실패가 있으면 성공 수정안으로 채택하지 않는다. |
| 5 | 독립 풀이의 다양성과 효율 확인 | 1회·2회·3회를 같은 총 시간으로 비교하고, 반복되는 동일 오답과 실제 다른 풀이의 비율을 기록한다. |
| 6 | 같은 하네스에서 27B/125B/클라우드 비교 후 학습 | 검증된 풀이의 전체 patch·명령·테스트 근거를 보관한다. 보지 못한 과제에서 교훈 효과를 확인한 뒤 켠다. |

현재 자동 문맥 예산은 16K의 24,000자를 64K에서 96,000자로 키운다. 약 120,000자인 `core.py`는 여전히 발췌될 수 있으므로 `coding_context_char_budget`와 프롬프트 여유를 함께 설정해야 한다. 기존 전체 파일 읽기의 100KB 제한도 있어 탐색에는 범위 읽기가 필요하다. 모든 파일을 한꺼번에 큰 문맥에 넣기보다 실제 누락 API·사용처를 찾는 흐름을 먼저 검증한다.

현재 provider는 `num_ctx`, `num_predict`, `num_gpu`를 전달하지만 sampling/seed를 명시적으로 기록·제어하지 않는다. 독립 시도를 늘렸다는 사실만으로 충분히 다양한 답이 생성됐거나 같은 조건의 재현이 가능하다고 판단하지 않는다. 현재 outcome의 diff는 2,000자로 잘리므로 추후 학습에는 원본 artifact 참조와 전체 풀이 기록이 필요하다. `/dev-learn`의 교훈 반영은 프롬프트 변경이며 모델 가중치 학습은 아니다.

## Sonnet 5 수준의 판정

Sonnet 5는 Anthropic 공식 문서에서 확인된다. Qwen 공식 모델 카드의 코딩 점수는 모델의 잠재력을 판단할 참고 자료다. 그러나 SWE-bench Pro의 과제 오류를 수정해 재평가했다는 각주, DeepSWE의 256K·두 하네스 중 최고 점수 조건을 함께 읽어야 한다. 설치된 양자화 모델·ALEX 하네스가 동일한 성능이라는 결론은 나오지 않는다.

ALEX와 Sonnet을 동일한 미공개 과제 복사본·허용 도구·테스트·예산에서 비교한다. 사람 도움 없는 엄격 성공률, 새 회귀, 처리 시간, 개입 횟수를 각각 보고하고 과제별 결과를 대응시킨다. 작은 파일럿은 개선 신호를 확인하는 용도다. 일반적인 Sonnet 동급 성능이라는 주장은 충분한 새로운 과제와 반복 평가 전에는 유보한다. 125B 평가 시작이나 긴 문맥 설정 활성화는 이번 검토에서 수행하지 않았다.
