작성: Claude(클라우드 세션, PC·모델 없이). 브랜치 `ccr-75791893-0vhkrr`, PR #1(초안). `main` 은 바뀌지 않았다.

2026-10-27 Codex 검토 보완: 코드 보완·측정 판정 기준·남은 제약은 8절에 기록했다. 실모델 우위는 여전히 확인하지 않았다.

**검토하는 AI 에게:** 당신은 독립 검토자다. 작성자(Claude)에게 동의만 하지 말고, 틀렸거나 과하거나 빠진 것을 찾아라. 이 문서의 주장은 아래 '근거' 에 적은 파일·커밋·검사로 확인할 수 있어야 한다. 확인할 수 없는 주장은 그렇다고 지적하라. 실제 모델로 잰 성능은 이 문서에 없다(클라우드에 그래픽카드가 없다) — 성능 우위를 주장하는 문장이 있으면 틀린 것이다.

## 1. 사용자가 정한 방향

- ALEX 는 '성장하는 AI' 다. 바깥의 좋은 에이전트를 **도구로 쓰는 것이 아니라 필요한 능력을 흡수**해 자란다.
- OpenCode(코딩 에이전트)와 Hermes Agent(스스로 배우는 개인 에이전트)의 능력은 **확실히 필요한 능력**이다. ALEX 는 처음 프로토타입에서 이 능력들을 흡수해 발전했다.
- 흡수한 부분은 **원본의 업데이트를 꾸준히 확인**해 필요한 것은 업그레이드하고, 아닌 것은 두고, 더 좋은 것이 있으면 변형도 해 본다.
- 걱정: **쓸데없이 덩치만 커지는 것.**

이 보고서는 위 방향을 운영 가능한 절차로 만든 것과, 그 절차를 처음 돌려 본 결과다.

## 3. 덩치 방지 규칙

가설: 결론 안 난 실험과 중복 구현이 유지보수 비용을 키울 수 있다. vulture 후보 21개는 대부분 프레임워크가 부르는 함수였지만, 이 정적 분석만으로 사용 빈도나 덩치의 주원인을 입증하지는 못한다. 사용 기록·변경 빈도·같은 수정을 여러 구현에 하는 비용을 함께 확인해야 한다.

| 원 보고서 기준 규모 | 숫자 |
|---|---|
| 파이썬 / 화면 / 시험 | 약 31,000줄 / 3,300줄 / 24,500줄(`core.py` 4,217줄, `web.py` 2,663줄) |
| 슬래시 명령 / 설정 | 95개 / 101개(기본 꺼짐 켜고 끄기 16개) |
| 결론 안 난 실험 | 7개 — `stable_prompt_prefix`, `coding_insights_enabled`, `coding_auto_learn_enabled`, `fact_reminder_enabled`, `coding_api_map_enabled`, `coding_regression_check`, `coding_diagnostic_context` |
| 같은 일의 여러 길 | 코드 고치기 4갈래 — 예전 모델 수정안(`coding_worker=alex`), OpenCode 일꾼(`opencode`), ALEX 하네스(`harness`), 클라우드 넘기기(`/cloud`) |

규칙:
1. **흡수에는 버리기가 포함된다.** 실험마다 결정할 날(`decide_by`, 지금은 모두 2026-11-30 — Claude 가 제안한 날짜이며 사용자가 정한다)까지 사전에 정한 기준으로 측정한다. 채택하면 겹치는 구현을 정리하고, 탈락하면 새 기능을 지운다. 동률·측정 불가이면 현재 기본값을 유지하고 이유·다음 과제·새 기한을 남긴다. 안전 검사는 동등한 대체 검증 없이 지우지 않는다.
2. **같은 요구조건을 충족하는 구현을 하나로 줄인다.** 오프라인·비공개 실행과 사용자가 선택하는 외부 전송은 서로 다른 요구조건이다. 기능 이름이 같다는 이유만으로 함께 없애지 않는다.
3. **핵심 능력은 흡수한 채 원본을 따라간다**(OpenCode·Hermes). `check_upstreams.py` 는 등록된 파일의 변경을 감지한다. 태그 추적 범위 밖의 새 정식 판도 알리지만, 미등록 의존 코드와 보안 공지는 별도 검토가 필요하다.
4. **덩치를 눈에 보이게.** 업데이트마다 `check_upstreams.py` 보고서(줄 수·명령·설정·지난 결정일)를 남긴다. 늘었으면 이유가 있어야 한다.
5. (아직 안 만듦) **쓰는지 기록.** 이 PC 안에서만 명령·기능 사용 횟수를 세어 석 달 안 쓴 것을 정리 후보로 — 개인정보 경계를 먼저 정해야 해서 이번에는 넣지 않았다.

## 6. 확인하지 못한 것·한계

- **실제 모델 성능·품질은 하나도 재지 않았다.** 프롬프트 순서가 실제로 빨라지는지, 답이 나빠지지 않는지, 평가 과제 점수는 PC 에서만 알 수 있다.
- Windows 전용 동작(opencode.exe, taskkill, 소켓 강제 닫기)은 Linux 에서 확인하지 못했다.
- 주입 패턴 검사는 어림이다 — 말을 조금 바꾸면 피한다. 승인 구조도 모델 출력·셸 실행의 완전한 격리를 보장하지 않는다. 문서 85개의 오탐 0건은 그 표본에만 해당한다.
- 대화 본문 검색은 색인 없이 훑는다. OR 조건에 걸린 최근 후보 2,000개를 먼저 자르고 점수를 매기므로 오래된 정확한 일치가 누락될 수 있다. 데이터가 많아질 때 지연시간과 검색 누락을 함께 측정해야 한다.
- `decide_by` 날짜는 Claude 의 제안이다.
- OpenCode v2(이미 배포, 흡수한 원본 파일 45개 자리가 모두 바뀜)로 기준을 옮길지는 정하지 않았다 — 10절.
- 규칙 5(사용 횟수 기록)는 아직 없다.
- 무료 모델용 파일 필터는 실행 격리가 아니다. 바이너리 본문·알려지지 않은 비밀값은 놓칠 수 있다. 자식 프로세스와 테스트는 여전히 현재 사용자 권한으로 실행되므로 원본·홈 파일·네트워크에 접근할 수 있다.

## 8. 검토 반영과 측정 판정 기준

### 코드로 보완한 부분

- `jarvis/egress.py` 로 무료 모델용 파일 선별·복사·변경 반입 정책을 모았다. 자동 수정 일꾼과 코딩 세션 모두 개인 데이터·기록·도구 폴더·비밀 파일·심볼릭 링크를 제외하며 300MB 상한을 공유한다. Windows reparse point도 제외 대상으로 분류하지만 실제 junction 동작은 Windows에서 확인해야 한다.
- 복사에서 제외한 파일·디렉터리 자리에 새 파일을 써도 원본에 반입하지 않는다. 작업 후 결과를 읽을 때도 링크를 따라가지 않는다. 검사와 복사 사이에 원본이 바뀌는 공격을 막는 운영체제 경계는 아니다.
- 무료 모델용 자식 환경변수는 실행에 필요한 플랫폼·프록시·CA 목록만 전달한다. API 키·클라우드 자격증명·Python 경로·주입된 OpenCode 설정은 상속하지 않는다. 홈 경로·프록시 설정은 남으므로 파일 접근이나 프록시 자격증명까지 격리하는 기능은 아니다.
- 원본 점검은 `ref`의 실제 SHA와 고정 `commit`을 대조한다. 실패한 원본을 보고서에 남기고 다른 원본 점검을 계속한 뒤 종료 코드 1을 반환한다. `checked`는 마지막 사람이 판정한 날짜이며 단순 조회 성공으로 갱신하지 않는다.
- OpenCode `v1.*` 비교를 유지하며 다른 주요 버전의 숫자 정식 태그도 알린다. 매월 점검 때 목록의 `releases_url`·`security_url`을 사람이 확인하고 미등록 코드 영향과 판정을 `history`에 남긴다. 태그 알림만으로 보안 점검 완료로 취급하지 않는다.

### 측정과 채택

`docs/upstreams.json`의 `evaluation_policy`·실험별 `accept`는 PC 측정 전에 확정할 제안이다. 이번 보완으로 실험 기본값을 켜거나 일꾼을 삭제하지 않았다.

1. 소스 SHA·모델/양자화·서버 버전·문맥/출력 상한·추론 옵션·검사 명령을 고정한다. 원본 데이터와 집계 결과를 함께 남긴다. 오류·skip·시간 초과·완료 증거 없는 검사를 성공으로 세지 않는다.
2. 같은 과제를 조건별 4회씩 비교하고 끔/켬과 켬/끔 순서를 번갈아 배치한다. 평가 전에 교훈을 고정해 과제 정답이 새 교훈으로 유입되지 않게 한다. 11개 과제 결과는 범용 성능 증거가 아니므로 별도 보류 과제로 재확인한다.
3. 프롬프트 측정은 `python -X utf8 scripts/measure_prompt_cache.py --live --pairs 4`. 매 실행 준비 요청을 제외하고 같은 시각 변화·고정 대화 기록으로 로컬 general 모델 하나를 스트리밍 호출한다. 실제 출력은 품질 검토용으로 저장하고 다음 차례에는 고정 답을 재생해 입력 차이를 막는다. 라우터·도구를 포함한 앱 전체 속도 측정은 아니다.
4. 둘째~여섯째 차례의 실행별 첫 글자 시간 중앙값을 짝지어 비교한다. 4쌍 중 3쌍 이상 개선·전체 중앙값 10% 이상 단축을 제안 기준으로 삼는다. 입력/출력 토큰과 답을 함께 검토한다. 서버 캐시는 초기화하지 않았으므로 cold-cache 성능이나 캐시 적중률은 주장하지 않는다.
5. FIFO 외 주제·사용자 교정·긴 문맥에서 품질을 별도 확인한다. 장기 메모·교훈·자료의 클라우드 제외, 소유권·승인 보호에 새 실패가 생기면 속도가 좋아도 채택하지 않는다. 출력 품질은 같은 질문의 두 답을 설정 이름을 가리고 평가한다.
6. 회귀 검사는 심은 회귀 10건 이상을 모두 찾는지와 정상 과제의 오탐을 확인한다. 실행 비용은 보고하되 빠르다는 이유만으로 보호를 없애지 않는다. 동률·자료 부족은 보류 이유와 다음 검증을 남기며, 날짜 경과만으로 자동 삭제하지 않는다.

`ci/verify` 가지(PR #2)의 GitHub Actions 를 이 가지에 합쳤다. 누가(사람·Claude·Codex) 어느 가지에 올리든 깨끗한 가상 컴퓨터에서 같은 검사를 다시 돌린다.

- `verify.yml`: `verify_release` — Ubuntu Python 3.10(최소 판을 실제로 실행)·3.11·3.13, Windows 3.11 / Chromium 웹 화면 검사(가짜 모델).
- `secrets.yml`: 저장소 역사 전체를 gitleaks 로 검사(시험용 가짜 키·가림 문자열만 허용, `.gitleaks.toml`).
- CI 가 처음 잡은 실제 버그: Windows 짧은 경로(`C:\Users\RUNNER~1`)와 풀린 경로를 비교해 시험 파일 쓰기를 거부하던 `developer._test_path` — 고쳤다.
- 모델·그래픽카드가 없으므로 실제 모델 품질·속도는 여전히 PC 에서 잰다.
