## 2. 우선순위 1 — 미검증·취소가 통과가 되는 경로 차단

### 2.1 확인한 버그

`jarvis/developer.py`의 `DeveloperMode._regressions`(스냅샷 978행)는 전체 검사가 124/125/126/130으로 끝나면 `baseline['skipped']`만 적고 `None`을 반환한다. `None`은 정상적으로 새 실패가 없을 때도 쓰인다. `_auto`(876행 근처)는 이 값을 받으면 `passed = True`로 바꾸고, 수정안이 있으면 최종 `awaiting_approval`로 보낸다. `auto()`의 결과 기록도 `copy_passed`가 된다.

뜻은 각각 시간 초과·실행 불가/0개 검사·로그 상한·사용자 취소다. 특히 취소는 다음 회차 시작 전 확인만으로 막을 수 없다. 통과 분기에서 반복을 끝내므로 그 확인에 도달하지 않는다. 실제 파일 자동 적용은 하지 않지만 **검증을 마친 제안처럼 표시·기록할 수 있는 문제**다. 설정 `coding_regression_check`가 켜진 경로에 해당한다.

추가로, 수정 전부터 실패가 있으면 테스트 이름의 집합 차이만 본다. 후보의 실패 이름을 로그에서 읽지 못하면 빈 집합이 되어 새 실패 없음으로 분류할 수 있다. `_run_bounded`는 로그 뒤 3,500자만 반환하므로 실패 이름 누락이 가능하다. 덜어내기 후 `_regressions` 호출도 같은 `None` 판정을 사용한다.

### 2.3 구현 계약

권장 구조는 `RegressionResult`와 부수 효과 없는 판정 함수다. 아래 이름은 구현 제안이며 기존 이름과 충돌하면 바꿔도 된다.

```python
@dataclass(frozen=True)
class RegressionResult:
    status: str  # verified | new_failures | unverified | cancelled
    reason: str
    new_failures: tuple[str, ...] = ()
    output: str = ""
```

| 상태 | 자동 루프 동작 | 제안/기록 |
|---|---|---|
| `verified` | 선택 테스트도 통과했으면 다음 단계 | 검사 범위를 명시하고 통과 후보로 인정 |
| `new_failures` | 남은 수정 횟수 안에서 구체적 실패를 모델에 전달 | 최종 통과로 기록하지 않음 |
| `unverified` | 추가 LLM 수정이나 독립 풀이를 시작하지 않고 종료 | `needs_test`, 원인·종료 코드 저장. `copy_passed` 금지 |
| `cancelled` | 원본/임시 복원 정리 후 즉시 중단 | 취소로 기록, 최종 제안 생성 금지 |

세부 규칙:

1. 124/125/126은 `unverified`, 130 또는 설정된 `cancel_event`는 `cancelled`. 원본 기준 검사에도 똑같이 적용한다. 취소 상태를 시간 초과보다 우선한다.
2. 정상 전체 검사 통과는 현행 `_run_unittest`의 0개/전부 skip 방지 계약을 유지한다. 검사 대역도 실제 출력 계약을 따르게 한다. 빈 출력의 `exit 0`을 임의로 검증 완료로 취급하는 새 우회로를 만들지 않는다.
3. 기존 실패를 제외하려면 후보·기준 양쪽의 실패 목록이 완전해야 한다. 아래 보수적 출력 판정부터 구현하고, 이름을 못 읽었을 때 빈 집합으로 통과시키지 않는다.
4. `coding_regression_check=False`에서는 기존 선택 테스트만의 동작을 유지한다. 다만 구조화된 결과에 `verification_scope='selected_tests'`를 적어 전체 검사 결과와 구분한다. True에서 미검증이면 선택 테스트 통과로 격하해 제안하는 fallback을 두지 않는다.
5. 별도 `verification_status`, `verification_scope`, `verification_reason`을 자동 루프 결과/회차 기록에 추가한다. 기존 소비자가 읽는 `result` 값은 통과/중단/실패 의미를 유지한다. 적용 후 `/dev-check`용 `suite_result`를 복사본 검사 결과로 덮지 않는다. 예전 저장 데이터에는 새 필드 기본값이 필요하다.
6. 기준 검사 중 후보를 원본으로 바꿨다면 `finally`에서 후보와 새 파일을 반드시 복원한다. 취소 때도 동일하다. 미검증 기준을 정상 기준처럼 캐시하지 않는다.

### 2.4 실패 목록의 완전성 — 최소 구현 범위

새 외부 패키지나 전체 테스트 실행기 교체 없이, 전체 검사 출력에서 표준 unittest의 완료 요약을 판독하는 작은 함수를 만든다.

- `Ran N tests`, 최종 `OK ...` 또는 `FAILED (...)`, failure/error 개수를 일관되게 판독한다. 마지막 완료 요약을 기준으로 하고 생략·깨진 요약·코드와 요약 불일치는 미검증이다.
- 실패 비교를 허용하려면 `FAIL:`/`ERROR:` 헤더 **발생 개수**가 요약의 failures + errors와 맞고, 각각에서 ID를 파싱할 수 있어야 한다. 중복 ID를 집합으로 바꾸기 전에 개수를 검사한다. subtest 형식을 확실히 지원하지 못하면 미검증으로 남긴다.
- 뒤 3,500자에 모든 헤더가 남지 않은 경우에도 미검증이다. 로그 상한을 무작정 늘려 해결하지 않는다.
- 정상 기준에서 후보가 명백히 실패했으나 ID를 읽지 못하면 `new_failures`의 일반 설명으로 반환해 재수정할 수 있다. 반대로 **실패 중인 기준과의 비교가 불완전하면 `unverified`**다.
- 완전한 양쪽 실패 ID가 같으면 현행 의미인 “새로 실패한 테스트 ID 없음”으로만 기록한다. 같은 ID의 실패 원인 악화까지 검증했다는 문구를 쓰지 않는다.

후속 개선으로 구조화된 unittest 결과 파일을 만들 수 있지만 이번 필수 범위에 넣지 않는다. 우선 보수적으로 미검증을 드러내고 실제로 미검증이 잦을 때 결과 수집기를 확장한다.

### 2.5 덜어내기와 최종 제안 경계

- `_trim`이 변경했는지 한국어 설명의 `"덜어냄"` 포함 여부에 의존하지 말고 전후 실제 바이트 해시 또는 명시적 `changed`로 판단한다.
- 선택 테스트·전체 검사 통과 후 덜어낸 후보는 다시 확인한다. 새 실패/미검증이면 **직전 검증된 후보의 정확한 바이트로 복원**하거나 전체 작업을 미검증으로 끝낸다. 검증된 후보로 복원해서 제안하는 경우 그 사실과 덜어내기 검사 결과를 기록한다.
- 검증된 후보는 변경/생성 파일과 합격 테스트 해시로 식별한다. 다른 내용에 검사 결과를 재사용하지 않는다. 기존 실제 파일·테스트 변경 감지도 유지한다.
- 덜어내기 중/뒤 취소는 이전 통과 결과가 있어도 중단한다. 최종 `create_bundle` 직전과 생성 직후 확인해, 그 사이 취소되면 제안을 discard하고 승인 대기로 저장하지 않는다. 취소하지 않은 경우에만 결과를 공개한다.

| 최종 제안 직전/직후 취소 | 저장된 대기 제안이 남지 않음 |
| 설정 False·예전 저장 데이터 | 기존 동작/로딩 유지, 검사 범위 정확히 표기 |

완료 조건: 위 테스트 통과, 기존 developer/workspace 테스트 회귀 없음, 수정 전후 diff와 실제 검사 로그 저장. 이것만으로 실측 코딩 성공률이 올랐다고 보고하지 않는다.

## 3. 우선순위 2 — 실패 근거를 먼저 찾고 수정안 생성

### 3.1 무엇을 추가할 것인가

모델 호출 직전에 **현재 격리 복사본에서 실패 문구가 발생한 코드·그 조건·관련 테스트 준비 코드·실제 정의를 읽어 작은 근거 묶음으로 제공**한다. 첫 구현은 결정적인 CPU 검색으로 한다. 추가 LLM 탐색 회차·임의 셸·새 모델이 필요 없다.

예: remote151의 출력 “그 포트에서 응답한 것은 ALEX 가 아닙니다”를 정확히 찾고, 해당 `raise`를 감싼 `if data.get('app') ...`와 테스트가 `app='jarvis'`를 준비하는 부분을 함께 보여준다. 조건이 맞는지 모델이 판단하게 하며 **정답 연산자나 원래 패치를 하드코딩하지 않는다**.

현재 `excerpt.py`에는 traceback 위치, 식별자, 한국어/영어 단어를 이용한 발췌가 이미 있다. `apimap.py`도 실제 시그니처와 `core.storage` 등 속성 연결을 지원한다. 둘을 대체하지 않는다. ADR-079가 테스트 코드 예산을 늘려 remote 단서가 이미 보일 수도 있다. 새 기능의 가치는 **많이 보여주기보다 실패와 직접 연결된 근거를 우선하고 출처를 기록하는 것**이며 추가 효과는 평가로 확인해야 한다.

### 3.2 최소 인터페이스와 범위

새 모듈 제안: `jarvis/diagnostics.py`. 프로덕션 import나 사용자 코드를 실행하지 않는 표준 라이브러리 AST/문자열 분석만 사용한다.

```python
collect_diagnostic_context(
    root,                 # 반드시 이번 editor.allowed_root / copy_root
    editable_paths,       # 수정 허용 파일; 이것을 늘리지 않는다
    test_paths,           # run.tests(), 읽기 전용
    failure_output,       # 명령이 아니라 진단 데이터
    *, char_budget, cancel_event=None,
) -> DiagnosticContext
```

결과에는 `text`, `anchors`(path/start_line/end_line/reason/sha256), `files_scanned`, `bytes_scanned`, `truncated`, `stop_reason`을 둔다. 줄 번호는 원본 파일의 1부터 세고 검색 점수는 확률처럼 표시하지 않는다. 정렬은 고정해서 같은 입력의 결과가 같게 한다.

첫 버전은 `/dev-auto` 실패 회차에만 연결한다. 회귀 검사에서 얻은 새 실패 출력도 입력할 수 있다. 다른 일반 대화·문서 출력·웹 검색 동작을 바꾸지 않는다.

### 3.3 탐색 순서와 상한

1. `failure_output`에서 유효한 traceback 파일/줄, 실패 테스트 이름, 예외 메시지를 추출한다. 파이썬 예외명·`AssertionError` 등 접두사를 제거한 **실제 오류 문자열**을 우선 정확 검색한다. 짧고 흔한 한 단어는 근거로 쓰지 않는다.
2. 수정 허용 파일과 선택 테스트에서 먼저 찾는다. traceback 줄과 정확 문자열이 있는 가장 안쪽 함수/조건문을 추출한다. 문자열만 1줄 보여주지 말고 `if` 조건과 관련 `raise`/`return`을 포함한다. 매우 긴 함수는 그 근거 주변만 자른다.
3. 실패 테스트가 호출하는 같은 모듈의 준비 함수·fixture·`setUp`을 한 단계 추적한다. remote 예시처럼 테스트 함수 밖에 준비된 입력을 놓치지 않게 한다. 객체/함수의 실행은 금지한다.
4. 해당 코드가 실제로 import/참조하는 프로젝트 정의를 한 단계만 읽는다. `apimap.py`의 정의 연결 로직을 재사용하거나 공통 함수로 최소 분리한다. 시그니처는 기존 API 블록과 중복하지 않고, 필요하면 선택된 메서드 본문의 짧은 부분/반환 계약만 보강한다.
5. 못 찾은 경우에만 승인된 루트 내 Python 파일을 제한 검색한다. `SafeFileSearchTool`은 이름 검색이므로 본문 검색과 혼동하지 않는다. 기존 `SafeProjectContextTool`의 경로·민감 파일 제외 정책을 재사용한다.

제안 상한: 최대 80개 파일, 파일당 200KB, 합계 4MB, 직접 연관 정의 깊이 1, 출력 최대 12개 구간·8,000자, 중간 파일마다 취소 확인. 시간 상한 2초는 보조 종료 조건이며 파일·바이트 상한을 함께 둔다. 이 숫자는 새 실측치가 아니라 최초 구현의 상한 제안이다.

절대 경로·`..`·루트 밖 resolved path·심볼릭 링크/Windows junction을 거부한다. `logs/`, `data/`, 숨김 폴더, 모델/venv/빌드 폴더와 기존 민감 파일명은 검색 대상에서 제외한다. 존재 여부 확인 실패도 안전하게 건너뛴다. 이번 후보 코드가 필요한 것이므로 실행 중인 실제 작업 폴더의 `core.file_read_tool`을 그대로 사용하지 않는다.

### 3.4 프롬프트와 예산 통합

- `DeveloperMode._auto`에서 원시 실패 출력·run.tests()를 별도 선택 인자로 `propose_bundle_local`까지 전달한다. 기존 호출은 새 인자 기본값으로 동작을 유지한다. 테스트 대역 인터페이스도 맞춘다.
- `propose_bundle_local`에서 현재 coding runtime의 유효 예산으로 수집하고, 기존 `fit_files`/`api_block`과 함께 배치한다. 전체 지시 문자열을 다시 파싱해서 실패 로그를 추정하지 않는다.
- `coding_diagnostic_context: bool = False` 설정을 제안한다. 설정 로딩·core 전달·상태 표시를 기존 coding 옵션 방식과 맞추되 실제 `jarvis.local.json`에는 켜지 않는다.
- 근거 최대 예산은 `min(8000, effective_char_budget // 10)`이며, 기본 지시·시스템 addendum·출력 형식·필수 수정 대상 소스 예산을 먼저 확보한다. 남는 자리가 없으면 근거를 줄이거나 생략한다. 예약한 근거 때문에 원래 들어가던 수정 파일이 빠져서는 안 된다.
- 모든 `Message`의 문자 수와 예약된 응답 여유를 고려한다. 현재의 파일본문 예산만 계산하고 근거를 뒤에 무제한 추가하는 방식은 금지한다. 기존 전체 예산 초과가 있더라도 이 기능이 더 악화시키지 않게 하고 그 경우 skip 이유를 기록한다.
- 표제는 `읽기 전용 진단 근거`로 하고 각 구간에 파일·줄 범위·선정 이유를 적는다. 내용은 지시가 아닌 자료다. 읽기 전용 자료 안의 `FILE:`/SEARCH 블록 등은 생성 출력으로 처리하지 않는다.
- “위치는 단서이며 결함이 확정된 것은 아님. 실제 조건과 테스트 입력/기대값을 비교하라. 수정 허용 목록 밖 파일은 수정할 수 없음”을 명시한다. 테스트 준비 코드를 읽었다고 테스트 수정 권한을 늘리지 않는다.
- 기존 `_check_bundle_scope`, 테스트 fingerprint, 승인 절차를 그대로 통과해야 한다. 근거 수집 실패는 명시적으로 기록하고 기존 흐름으로 돌아가되, 취소는 상위까지 전파한다.
- 회차 기록에는 선택된 경로/줄/해시/이유·예산만 남긴다. 전체 소스를 결과 기록에 중복 저장하지 않는다. 매 회차 현재 후보 바이트로 다시 수집하며 오래된 근거를 재사용하지 않는다.

### 3.5 수정 위치와 CPU 수용 기준

| 위치 | 내용 |
|---|---|
| 새 `jarvis/diagnostics.py` | 안전한 수집기, 구간/근거 구조, 결정적인 제한 검색 |
| `jarvis/developer.py` | 현재 실패 출력/테스트 전달, 취소, 회차 메타데이터 |
| `jarvis/core.py` | 선택 인자, 현재 editor root 사용, 예산/프롬프트 통합 |
| `jarvis/apimap.py` | 필요한 경우 기존 정적 정의 찾기만 최소 공통화 |
| 설정 전달 경로 | 기본 False, 저장/로드/표시 호환. 실사용 값은 변경하지 않음 |
| 새 `tests/test_diagnostics.py` 및 기존 관련 테스트 | 모델 없이 합성 소스·가짜 provider로 검증 |

필수 테스트:

1. 오류 문자열이 긴 파일의 뒤쪽에 있어도 주변의 실제 조건과 raise를 함께 선택한다. 상관없는 `deadline`, `local_only`만 선택하지 않는다. 특정 과제명을 코드에 넣지 않는다.
2. 테스트 기대값이 100줄 밖 준비 함수에 있어도 한 단계 연결로 선택한다. 없는 정의는 만들어내지 않고 못 찾았다고 기록한다.
3. `SafeFileReadTool.run(self, **kwargs)`의 시그니처만으로 부족하면 본문의 `kwargs.get("path", "")`까지 보여줘 실제 호출 `run(path=...)`의 근거를 제공한다. 존재하지 않는 `run(*, path=...)` 시그니처를 만들어내지 않는다. 기존 API 블록과 중복하지 않는다.
4. 읽기 전용 참조 파일을 수정하려는 모델 출력은 여전히 범위 검사에서 거부된다.
5. root 밖·symlink/junction·민감 파일명·악성 traceback/로그를 따라 나가지 않는다. 로그의 셸 문장을 실행하지 않는다.
6. 파일/바이트/시간/구간/문자 상한, 빈 로그, 문법 오류 파일, 읽기 실패, 중복 구간 병합, 취소를 검증한다.
7. 임시 후보와 실제 폴더의 같은 파일 내용이 다르면 **후보 내용**의 줄/해시가 들어간다. 수정 다음 회차에서 근거도 갱신된다.
8. False일 때 기존 프롬프트/모델 호출 수가 유지된다. True여도 추가 모델 호출이 없고, 작은 문맥에서도 파일 소스 예산을 침범하지 않는다.

### 3.6 성능 수용 기준 — 지금 GPU로 실행하지 말 것

다음 평가 기회에 Claude의 최신 코드·동일한 모델/문맥/층수/시도 수/테스트를 고정하고 **진단 근거 False 대 True 한 변수**만 비교한다. ADR-079 이전 수치와 직접 비교해 새 기능 효과라고 주장하지 않는다. 같은 고정 과제 목록과 기준 해시를 보존하고 실행 결과는 새 경로에 저장한다.

- remote151: 최초 수정 위치, 조건/테스트 입력을 실제로 함께 보았는지, 수정 횟수와 엄격 통과를 비교한다.
- API/역사 과제: 이미 ADR-079가 해결한 것은 추가 개선으로 세지 않는다. 필요한 정의를 못 찾는 남은 사례를 중심으로 본다.
- 성공률, 회귀 유무, 총 시간, 모델 호출 수, 유효 문맥 크기, 거부 횟수를 함께 보고한다. 같은 과제의 반복은 독립적인 새 과제 수로 합산하지 않는다.
- 작은 표본에서는 “원인 후보/개선 신호”로 보고하며 기본값은 False 유지. 최신 기준보다 새로 엄격 실패하는 사례가 생기거나 근거 비용 대비 개선이 없으면 기본 활성화를 보류한다.

통과한 증상 우회(`_truncate_text` 작은 limit)와 환경변수 복원 누락은 별도의 **테스트 계약 사각지대**다. 1번이나 2번만으로 해결된다고 주장하지 않는다. 이후 평가 버전에서 경계값/환경변수 계약을 보강할 수 있으나 진행 중 과제·합격 테스트를 바꿔서 점수를 올려서는 안 된다.

## 5. 결과 보고 형식

구현자는 기능별로 (1) 변경 파일과 백업 (2) 검사 명령·실제 결과 (3) 현재 코드/후보 해시 (4) 미검증 범위 (5) 평가나 반영을 이어갈 정확한 다음 단계만 정리한다. 새 설정 활성화·GPU 평가·전체 검증·재시작을 하지 않았으면 하지 않았다고 쓴다. 기존 평가 로그나 이 문서의 재현을 새 구현의 테스트 결과로 재사용하지 않는다.
