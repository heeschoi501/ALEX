## 발견 사항

### R2-01 · P1 · 사후 증거가 같은 run의 다른 수정안으로 넘어간다

**위치:** `diff:299–310`, `jarvis/insights.py::after_evidence`; `diff:426–430`, 평가 suite 이벤트 내보내기.

`applied`만 proposal ID로 거른다. 선택 검사와 전체 검사는 해당 auto 이후의 모든 이벤트 중 마지막 값을 가져오며, 이번 패치가 추가한 digest를 사용하지 않는다. suite에는 `valid=False` 제외도 없다.

발생 순서: `auto(p1) → applied(p1,digest=A) → suite FAIL(A) → auto(p2) → applied(p2,digest=B) → suite PASS(B)`. p1의 사후 확인도 `전체 검사 PASS`가 된다. 반대 순서에서는 성공한 p1에 p2의 실패가 붙는다. 원인이 다른 수정안의 성공·실패를 잘못 학습할 수 있다. 한 run 안에서 여러 후보를 다루는 사용 흐름에서 발생하며, 과제마다 run이 하나인 현재 평가에서 이미 발생했다고 단정하지 않는다.

**보완:** auto의 proposal → 실제 applied의 digest → 같은 digest의 tests/suite를 연결한다. 지문 없는 옛 기록은 다음 proposal/apply 등 경계를 넘지 않게 하고, 연결을 증명할 수 없으면 전체 검사 미확인으로 남긴다. 평가가 추가하는 suite 이벤트에도 대응하는 적용 digest·proposal ID와 시각을 보존해야 한다. `source_hash`는 평가의 원본 소스 지문이므로 수정 후 후보 digest를 대신할 수 없다.

**후속 검사:** 같은 run의 p1 FAIL/p2 PASS와 그 반대, 폐기된 p1 뒤 p2 검사, 무효화된 suite, suite 없는 p1. 추가된 `diff:729–740` 검사는 후보 하나만 다뤄 이 경계를 확인하지 않는다.

### E2-02 · P2 · 전체 deadline의 남은 시간을 개별 검사에 전달하지 않는다

**위치:** `diff:628–640`, mutation 생성기; 변경되지 않은 `jarvis/developer.py:235–273`의 `_run_unittest/_run_bounded`.

모듈과 hard 조합 시작 전 시각 확인이 추가되어 제한 뒤 새 작업 시작을 줄인다. 그러나 남은 시간이 1초여도 `_run_unittest`는 별도의 120초 제한으로 시작한다. 따라서 `--max-seconds`를 엄격한 전체 상한으로 해석하면 검사 한 번의 제한 시간과 복구 비용만큼 초과할 수 있다. R04의 ‘남은 시간에 따른 개별 timeout’은 아직 구현되지 않았다.

후속 방향은 `min(기존 검사 제한, 전체 남은 시간)` 전달과 중단 후 원본 복구 보장이다. 별도 복사본에서 가짜 시계·runner로 확인하면 되고, 이를 확인하려고 현재 장시간 평가를 시작할 필요는 없다.

### E2-03 · P2 · hard 결합 뒤 문법 오류를 논리 버그 과제로 저장할 수 있다

**위치:** `diff:636–652`; 변경되지 않은 `logs/probe/mutation_tasks.py:168–172`와 `193–206` 비교.

단일 변이에는 `ast.parse(mutated)`가 있지만 두 변이를 합친 뒤에는 없다. 두 개의 대입만 있는 함수에서 각각 한 대입을 삭제하는 변이가 개별적으로 테스트를 실패시켰다면, 둘을 함께 삭제했을 때 함수 본문이 사라져 SyntaxError가 된다. unittest의 import ERROR도 exit=1이므로 hard 과제로 채택될 수 있다. 문법 복구가 목적이 아니라 두 논리 결함 복구를 재려는 데이터셋이라면 난도·유형이 섞인다.

후속 방향은 결합 후에도 문법을 검사하고 import/수집 오류를 논리 assertion 실패와 구분하는 것이다. 예시 입력은 `def f():` 아래 `a = notify_a()`와 `b = notify_b()`만 있고 각 호출을 확인하는 테스트다. 이는 현재 hard 결과에 해당 오류가 실제 존재한다는 주장이 아니라 생성기의 필터 누락이다.

## 함께 남길 해석 주의점

- `diff:286`은 전체 FAIL이면 ‘다른 곳을 깨뜨린 까닭’을 찾으라고 지시한다. 실패를 최종 성공으로 배우지 않는 것은 맞지만 **수정이 실패의 원인이라고 확정할 근거는 별도**다. 실제 train app 과제는 `restored_original=true`인데 전체 검사 실패가 한 건 기록됐다. 엄격 성공에서는 제외하되 수정 유발 회귀인지 간헐/환경 실패인지는 미확정으로 입력하는 편이 정확하다. [완료 train·교훈 분석](CODEX_TRAIN_INSIGHTS_ANALYSIS_20260930.md)을 함께 볼 것.
- `_files_digest`는 run.files()만 해시한다. 다른 의존 파일이나 테스트만 바뀐 경우까지 전체 suite 증거를 보장하는 지문은 아니다. 이번 수정의 보장 범위를 명시하고, 전체 회귀의 버전 신뢰도가 필요하면 범위를 넓힌다.
- 이번 diff의 추가 테스트와 mutation self-test는 읽었다. 위 경계 사례가 diff에 없다는 사실은 Claude의 별도 검사 전체가 없거나 실패했다는 뜻이 아니다. 추가 검사 여부는 별도 복사본의 최신 결과에서 확인한다.

## Claude 재개 시 적용 순서

1. 실제 GPU 실험 종료와 최신 별도 복사본 상태를 먼저 확인한다. 예상 16시만으로 종료를 단정하지 않는다.
2. **기존 보완 패치를 다시 구현하지 말고** R2-01/R2-02를 중심으로 그 복사본에서 보완·검사한다. R2-03/R2-04/R2-05는 교훈 보존·재시도 계약을 함께 정리한다.
3. 나머지 사항은 위 범위의 작은 검사로 확인하고, 원본/변경 파일·실제 검사 결과를 인계에 갱신한다. 이 문서에는 정적 리뷰만 기록했으며 코드 적용·테스트 실행은 수행하지 않았다.
