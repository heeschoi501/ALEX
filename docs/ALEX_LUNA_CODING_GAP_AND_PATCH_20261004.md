# Luna 수준 코딩을 위한 ALEX의 부족한 부분과 수정 코드 제안

작성: 2026-10-04. 평가 사본: **18:06:48 KST**. 비교 목표는 현재 GPT-6 Luna로 해석했다.
사용자 요청: Luna 수준으로 코딩하기 위해 필요한 부분 확인, 현재 테스트에서 개선할 수 있는 부분 확인, 수정 코드 제안.

## 판단부터

**현재 ALEX가 Luna 수준이라는 근거는 없다. 그렇다고 모델 크기를 바꾸는 것만이 해법이라는 근거도 없다.** 지금 평가에서는 문제 범위·추가 코드 확인·테스트 계약이 실제 병목으로 드러났다. 이 중 두 가지를 별도 복사본에서 실행 가능한 수정안으로 만들었다.

GPT-6 Luna 공식 문서는 함수 호출·구조화 출력과 파일 검색·셸·패치 도구 등의 지원을 설명한다. 하지만 그것이 ALEX의 역사 과제에서 몇 개를 풀거나 특정 로컬 모델보다 얼마나 우수한지를 말해 주지는 않는다. 모델 자체의 추론 능력과 주변 도구·에이전트 동작을 분리해서 비교해야 한다. 출처: [OpenAI Docs — GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).

이번 작업에서는 Luna API나 로컬 LLM을 호출하지 않았다. 사용자 소스·데이터를 외부 모델에 보내지 않았고, Claude의 진행 중 평가도 변경하지 않았다.

- **과거 core 1679:** 증상 우회가 전체 테스트도 통과했다. 함수 계약 검사가 부족하다. 장문·더 큰 모델만으로 이러한 완료 판정을 해결할 수 없다.

“이 조건들을 구현하면 Luna와 동급”이라는 뜻은 아니다. 같은 모델도 도구가 부족하면 실패할 수 있으므로 시스템 병목을 줄인 뒤, 남은 모델 능력 차이를 평가하기 위한 조건이다.

## 수정안 A — 남은 기존 실패를 정확히 기록

코드 위치: [별도 복사본 developer.py](../logs/codex-luna-proposal-20261004/workspace/jarvis/developer.py).

`RegressionResult`에 다음 증거를 추가했다.

```python
baseline_failures: tuple[str, ...] = ()
residual_failures: tuple[str, ...] = ()

def evidence(self) -> dict:
    return {
        "baseline_failures": list(self.baseline_failures),
        "residual_failures": list(self.residual_failures),
        "completion": "residual_failures" if self.residual_failures else
                      "suite_passed" if self.status == "verified" else "not_verified",
    }
```

- 기존부터 실패했던 검사와 수정 후에도 남은 검사를 이름으로 기록한다.
- `verification_completion=residual_failures`와 `suite_passed`를 구분해 auto outcome에 저장한다.
- 사용자 결과에도 남은 검사 이름과 “목표 전체 완료 여부는 별도 확인”을 표시한다.
- trim 뒤 실제 후보가 바뀌어 재검증했으면 최종 증거도 갱신한다. 미검증이면 기존 검증 후보를 복원하는 동작은 유지한다.
- **새 실패가 없으면 허용하는 현재 정책을 유지**한다. 프로젝트의 무관한 오래된 실패까지 자동으로 고치는 기능은 추가하지 않았다.

이 수정은 완료 상태를 더 정확하게 보여 주는 첫 단계다. 목표 관련성 자동 판단이나 outcomes에 빠진 두 명령의 자동 복구를 구현한 것은 아니다. 다음 변경에서는 작업 manifest에 목표 관련 검사 목록을 명시하고, 해당 검사만 필수 완료 조건에 연결하는 편이 안전하다.

## 수정안 B — 모델이 요청한 코드 구간 추가 읽기

핵심 코드: [coding_reads.py](../logs/codex-luna-proposal-20261004/workspace/jarvis/coding_reads.py).
연결 코드: 별도 복사본 `core.py`, `config.py`, `app.py`, `developer.py`.

기본값은 `coding_context_reads=0`이며, 제안이 적용되고 검토자가 명시적으로 1~2로 설정할 때만 동작한다. **현재 실사용 설정은 바꾸지 않았다.**

모델은 수정 블록 대신 다음과 같은 명시적 요청을 낼 수 있다.

```text
READ_CONTEXT: {"path":"jarvis/web.py","start":420,"end":459}
```

처리 흐름:

1. 모델의 단일 JSON 요청을 검증한다. 자연어 설명 전체를 임의 실행 명령으로 해석하지 않는다.
2. 지금 후보가 있는 격리 복사본에서 요청 구간을 읽는다.
3. 경로·줄 번호·파일 해시와 내용을 자료로 전달한다.
4. 모델이 추가 근거를 반영한 수정 블록을 작성한다.
5. 기존 변경 블록·문법·범위·테스트·승인 검사를 그대로 거친다.

제안의 경계:

- `.py` 파일만, 1회 최대 80줄·파일 최대 200KB, 자료 블록 최대 1,800자. 추가 읽기는 생성 단계당 최대 2회다.
- 모델의 같은 구간 반복 요청은 중단한다. 남은 문맥이 부족한 요청을 조용히 잘라 전달하지 않는다.
- 숨김/민감 경로, 상위 경로 탈출, 절대 경로, 심볼릭 링크·Windows 재분석 지점은 거부한다.
- 추가 자료는 지시가 아닌 데이터로 전달한다. 읽었다고 기존 파일의 수정 허용 목록이 늘어나지 않는다.
- 기능이 켜지면 추가 근거를 위한 문맥 자리를 확보한다. 기존 파일 발췌량이 달라질 수 있으므로 효과 비교가 필요하다.
- 기본 꺼짐 경로에는 추가 모델 요청이나 프롬프트 지시가 없다.

이 제안은 **요청한 구간을 읽는 최소 기능**이다. 저장소 전체 검색·심볼 위치 탐색·자율 계획까지 구현한 것은 아니다. 모델이 파일과 줄을 모를 때 사용할 제한된 검색은 다음 단계다. 기존 자연어 “web.py를 보여 달라”를 그대로 자동 해석하지 않으며, 새 프로토콜을 실제 로컬 모델이 얼마나 잘 따르는지도 아직 미검증이다.

추가 읽기 상한은 이 보조 루프의 생성 단계 수다. 기존 공급자 fallback·생각 소진 재시도·변경 블록 형식 재질문까지 포함한 전체 네트워크 호출 상한과는 다르다. 전체 실행 deadline과 실제 호출 계수는 후속 개선 대상이다. 성공 경로의 읽기 증거는 회차 기록에 연결된다. 중간 취소/실패의 읽기 이력을 완전히 보존하는 추적 기능도 후속 보완이 필요하다.

## 이번에 제안하지 않은 즉시 변경

- 현재 진행 중 평가 과제·테스트의 수정: 완료 뒤 새 manifest 버전에서 해야 비교가 유지된다.
- 48K/추가 읽기를 실사용 기본으로 활성화: 성공당 시간·실패·문맥 감소를 먼저 비교해야 한다.
- 테스트 오류를 보고 자동 성공 처리하거나 통과할 때까지 무제한 재시도: 원인 미확인을 숨기게 된다.
- 테스트가 통과하는 방향으로 테스트 자체를 수정: 모델 후보의 성공 근거로 사용하지 않는다.
- 가중치 미세조정·모델 교체만으로 Luna 도달 선언: 현재 자료로 입증할 수 없다.

## 비교 평가 설계

두 가지를 분리해서 측정한다.

1. **모델 비교:** 같은 ALEX 하네스·도구·문맥 제공 정책·총예산으로 로컬 모델과 정확한 Luna 모델/추론 설정을 비교한다. 모델별 지원 문맥·토큰화 차이도 기록한다.
2. **제품 경험 비교:** 현재 ALEX와 사용자가 실제 쓰는 Luna 에이전트에 같은 작업을 맡긴다. 도구·권한·컨텍스트 차이를 함께 보고하므로 모델 자체의 우열로 해석하지 않는다.

현재 역사 11개는 회귀 점검에 유지하되, 목표에 맞는 미사용 과제(버그 수정·여러 파일 기능 추가·테스트 작성·리팩터링·환경 실패 구분)를 별도로 고정한다. 개발용으로 답을 분석한 과제를 최종 미사용 평가라고 부르지 않는다. 결과는 선택된 최종 수정의 기능 완성도·전체 회귀·의미상 올바름·사람 개입·소요 시간으로 비교한다. 임의로 “11개 중 10개면 Luna급” 같은 문턱을 만들지 않는다.

이번 수정안의 첫 효과 비교는 같은 로컬 모델에서 **추가 읽기 0 ↔ 1 또는 2**다. 기존 진단·API·문맥·소스·총예산을 고정하고, 실패한 경우도 포함해 실제 호출·정답·시간을 기록한다. GPU 실행은 이번 작업에서 하지 않았다.

## 제안 코드의 검증 결과

- 관련 5개 모듈의 **167개 검사 실행: 166 통과, 기존 잔여 실패 개수 문구를 고정한 검사 1개 실패**. 해당 사례는 수정 전 2개 중 1개가 해결돼 실제 잔여는 1개다. 잘못된 기존 표시를 보존하지 않고 테스트 기대값을 교정했다.
- 기대값 교정 후 **해당 기존 검사 1개+추가 검사 14개, 총 15개 모두 PASS**. 실행 코드 추가 변경 없이 기대값만 교정했고, 167개 전체를 재실행한 것으로 보고하지 않는다.
- 추가 검사는 실제 임시 후보 파일 읽기→수정안 생성, 원본 미적용, 읽기 후 쓰기 범위 제한, 반복·횟수·문맥·크기 상한, 경로·링크 거부, 취소, 기본 꺼짐, 기존 실패 이름·완료 상태 기록을 포함한다. 모델 응답은 결정적인 대역을 사용했다.
- 기존 범위: developer·coding_context·workspace_bundle·config. R1~R3 관련 기존 판정/취소 검사도 이 범위에 포함된다. 검증은 별도 workspace에서 실행했고 실제 모델·GPU·ComfyUI를 호출하지 않았다.
