# 완료 train·생성 교훈 분석과 전후 비교 기준 — 2026-09-30, Codex

## 범위와 확인 수준

완료된 train 35개 JSON, 대응 outcomes JSONL, 추출된 교훈 8개, 기존 baseline 16행, 과제 정의를 읽었다. 표준 라이브러리로 집계했으며 모델·ALEX 테스트는 실행하지 않았다. 진행 중 평가의 입력·출력·교훈은 수정하지 않았다. 11:26의 부분 관측 문서 [CODEX_EVAL_SNAPSHOT_20260930.md](CODEX_EVAL_SNAPSHOT_20260930.md)를 대체 삭제하지 않고, 완료 train 관측을 추가한다.

## 3. 생성 교훈 8개 내용 검토

아래는 `logs/coding-insights-train.json`의 현재 후보를 읽은 검토다. **원본 교훈을 바꾸거나 비활성화하지 않았다.** 실험이 끝난 뒤 별도 교훈 버전으로 보완하고, 현재 버전의 결과와 구분한다.

| ID / 점수 | 내용 요지 | 판단과 보완 방향 |

교훈 6의 sources에는 미해결 remote 과제가 포함된 배치가 있다. 실제 해당 실패에서 대기 래퍼를 우회하는 시도가 관측됐다. 다만 source는 여러 과제를 합친 배치 문자열이므로 **그 실패 하나가 교훈 6의 직접 원인이었다고 확정할 수 없다.**

교훈 3은 간단한 반례로 일반 규칙의 오류를 설명할 수 있다. 이 내용 검토가 이번 교훈 on 실험의 성적이 나쁘다는 뜻은 아니다. 실제 성적과 문장 타당성은 별도로 확인한다.

### 증거 추적의 제한

- `count`는 ADD/EDIT/UPVOTE/DOWNVOTE 연산으로 변한 점수다. 독립 성공 횟수나 성공 확률이 아니다.
- sources는 여러 과제 ID를 합친 뒤 120자로 자르고, 교훈별 최근 5개 문자열만 남긴다. 잘린 과제 ID도 있어 개별 교훈을 정확한 수정안·검사 결과로 추적하기 어렵다.
- learned 35개에는 auto 미해결 3개와 선택 통과/전체 실패 1개도 들어 있다. 실패에서 학습하는 것 자체는 가능하지만, 최종 증거가 빠지면 실패한 행동을 성공 규칙처럼 배울 수 있다.
- 후속 자료 계약은 교훈별 `run_id`, `auto_at`, `proposal_id`, 수정 digest, suite 결과, 근거 회차와 반례를 구조화해 연결하는 방향이 적합하다. 투표 횟수만으로 검증 등급을 올리지 않는다.

## 4. 현재 test 결과가 끝난 뒤 사용할 비교 기준

이 기준은 과거 baseline과 일부 진행 상황을 이미 본 뒤 정리한 감사 기준이다. 사전에 봉인한 평가 계획이라고 표현하지 않는다. 진행 중 test 결과를 최종 성적으로 발표하지 않는다.

1. **같은 보류 test 과제끼리 비교한다.** train 31/35와 baseline test 15/16은 서로 다른 문제 집합이므로 교훈 효과의 전후 비교가 아니다. train 실패를 개선 설계에 쓰되 최종 test를 반복 조정용으로 사용하지 않는다.
2. **16행과 15개 고유 ID를 구분한다.** baseline의 `mut_device_change_constant_25`가 두 행에 반복된다. 현재 task 파일은 각각 `_eaad`, `_ac3d`로 구분하며 같은 baseline_id를 가진다. 나머지 14개는 ID 매핑이 일대일이다. 두 충돌 행은 원래 변이·diff 등 추가 근거로 대응을 확인하기 전에는 순서로 붙이거나 임의 중복 제거하지 않는다. 대응 14개 표와 미해결 2개, 전체 16행 집계를 각각 표시한다.
3. **행의 상태를 성공·미해결·전체 검사 실패·미검증·운영상 중단으로 구분한다.** 엄격 성공 조건은 위 정의를 사용한다. 회귀의 원인까지 확정하지 못한 경우 ‘전체 검사 새 실패 기록’으로 표현한다. suite 누락/실행 오류를 통과로 세지 않는다.
4. **전이표를 남긴다.** 같은 과제의 실패→성공, 성공→실패, 그대로 성공, 그대로 실패/미검증을 표시한다. baseline이 15/16이라 개선 여지는 작고 새 실패 하나의 영향이 크다. 시간은 동일 과제별 차이와 중앙값, 합계를 구분하고 누락 시간을 0으로 채우지 않는다.
5. **실험 조건의 동일성을 별도 판정한다.** 원본/에이전트/harness, 과제 파일, 교훈, 설정, 모델 버전, ctx/KV/GPU 옵션, Python/의존성의 지문을 확인한다. 기존 실행은 live ROOT를 과제마다 복사했고 11:17 소스 수정도 있었다. 메타데이터로 동일 조건을 증명하지 못하면 탐색적 관측으로 남긴다. 나중에 적용할 고정 스냅샷 패치는 이미 만들어진 결과의 교란을 소급 제거하지 않는다.
6. **hard와 쉬운 test를 섞어 점수를 만들지 않는다.** 과제 정의·분할·버전과 난도를 명시하고, hard의 교훈 off/on도 동일 문제와 조건을 확인한다. 같은 함수에서 만든 관련 과제 수를 독립 표본 수처럼 해석하지 않는다.

권장 최종 표의 열은 `task/version`, `baseline_id`, `pairing 근거`, `off 상태`, `on 상태`, `전이`, `seconds off/on`, `전체 실패명`, `source/settings/insights 지문`, `해석 제한`이다. 기존 [compare_eval_results.py](../logs/probe/compare_eval_results.py)는 개별 JSON을 읽어 요약하는 도구이며, 중복 행을 자동 대응시키거나 인과 효과를 추정하는 도구는 아니다.

## 인계

지금 가능한 읽기 전용 분석과 문서화는 완료했다. 현재 실험에는 개입하지 않았다. 실제 실험 종료 뒤 최신 결과와 Claude의 별도 복사본 패치를 먼저 확인하고, 2차 리뷰의 증거 연결·보존·재시도 문제를 보완한다. 교훈 내용 수정과 효과 재평가는 별도 버전으로 진행하며, 이 문서의 후속 검사 제안을 이미 수행한 결과로 보고하지 않는다.
