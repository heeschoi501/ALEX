## 1순위 — 목표 관련 실패를 모두 확인하고, 테스트·환경 실패를 분리

### 실제 근거

**outcomes 과제:** v2는 `/dev-outcomes`를 복구해 지정 `test_developer`를 통과했다. 그러나 역사 과제가 되돌린 덩어리는 `/dev-learn`·`/dev-insights`도 지웠다. 그쪽 `test_insights`는 수정 전부터 실패했으며 끝까지 남았다.

자동 루프 기록은 다음과 같다.

```text
2회차 테스트: 통과 · 새로 실패한 테스트 ID 없음(수정 전부터 실패하던 2개는 그대로)
```

이는 현재 “새 회귀 없음” 정책에서는 맞는 판정이다. **R1~R3 판정 오류가 재발한 것이 아니다.** 반면 깨끗한 원본 기준의 평가에서는 기능 일부가 복원되지 않아 엄격 실패다. 기존 메모의 “후보가 test_insights를 새로 깨뜨렸다”는 해석은 Claude가 정정했고, 이번 코드·로그 검토도 이를 뒷받침한다.

**characters 과제:** 2,762초, 약 46분 뒤 실패했다. 마지막 모델 답은 형식 지시를 잊은 설명이 아니라 다음과 같은 범위·근거 요청이었다.

```text
jarvis/web.py 를 보지 못했습니다. 이 오류는 jarvis/core.py 로는 고칠 수 없습니다.
```

마지막 테스트 출력에는 `http.client.RemoteDisconnected`와 업로드 테스트 오류가 있다. 최초 `detected_failures`에도 업로드 오류가 섞여 있다. **수정 모델의 순수 추론 실패·테스트 환경 흔들림·실제 웹 결함 중 무엇인지 아직 분리되지 않았다.** 현재 소스를 실행해 재현하지 않았으며 원인을 확정하지 않는다.

### 구현 가이드

- `RegressionResult`·auto outcome에 `baseline_failures`, `candidate_failures`, `resolved_failures`, `residual_failures`, 검증 범위를 추가한다. 기존 `new_failures`와 함께 보관하고 결과 지문에 연결한다.
- 잔여 실패는 **목표 관련 / 목표 밖 기존 실패 / 환경 의심 / 관계 미확인**으로 나눈다. 분류 근거를 남기고 애매한 것을 자동으로 목표 밖이라 확정하지 않는다.
- 목표 관련 실패가 남으면 `새 회귀 없음`과 `목표 전체 완료`를 분리해 사용자에게 알리고, 허용된 작업 범위 안에서 그 실패 이름·테스트 기대값도 다음 수정 문맥에 제공한다.
- 목표 밖 기존 실패는 자동 수정하지 않는다. 목표 관련이어도 수정 허용 파일이 부족하면 범위 확대 요청 상태로 끝낸다. 현재의 승인 경계·테스트 변경 금지·미검증 처리·취소 처리를 유지한다.
- 평가 도구의 `bug_detected = code != 0`만으로 충분하지 않다. 같은 합격 검사에 대해 **버그 주입 전 실패 집합과 주입 후 실패 집합의 차이**를 기록한다. 주입 전 이미 실패한 사례는 유효성 확인 없이 새 버그 검출로 세지 않는다.
- 후보에서 연결 종료·timeout 등이 나오면 원인 미확인 상태로 구분한다. 다음 평가 버전에서 원본 대조와 같은 후보의 제한된 재확인 절차를 명시할 수 있지만, 재시도 중 한 번 통과했다고 앞선 실패를 지워 성공으로 세지 않는다.
- 평가 과제 정의도 정렬한다. outcomes처럼 여러 명령을 지우는 과제라면 지정 합격 기준에 해당 기능 검사를 포함하거나, 원래 intended scope를 기록해 부분 복원과 전체 복원을 나눈다. **진행 중 과제·테스트는 수정하지 않는다.**

수정 후보 위치: `jarvis/developer.py`의 `_regressions`·`_auto`·결과 기록, 다음 버전 `logs/probe/coding_agent_eval.py`와 역사 과제 manifest. 기존 typed 판정 구조를 확장하며 다시 구현하지 않는다.

### 수용 기준

1. 목표 관련 기존 실패가 남는 합성 사례는 “새 회귀 없음”일 수 있어도 목표 전체 완료로 표시하지 않는다.
2. 목표 밖 기존 실패는 그대로 남겨도 정책에 맞는 수정 결과를 유지하며, 무엇이 남았는지 표시한다.
3. 버그 주입 전후 동일한 기존 실패만 있는 평가 사례는 새 버그 검출로 집계하지 않는다.
4. 환경 의심 실패는 테스트 이름·출력·시점·원본/후보 지문을 보존하고 미확인으로 기록한다. 이를 모델 오답이나 통과로 단정하지 않는다.
5. 기존 정상 판정·취소·trim 후 재검증·승인 경계를 보존한다.

## 2순위 — 필요한 파일을 읽어 확인하는 제한된 탐색 루프

### 이미 있는 것과 새로 필요한 것

`jarvis/diagnostics.py`는 오류 문구·traceback·테스트 준비 함수를 **한 번 자동 수집**한다. API 요약도 이미 구현됐다. 둘을 재구현할 필요가 없다.

부족한 것은 모델이 “이 파일의 이 함수가 더 필요하다”고 판단했을 때, **현재 격리 후보의 실제 내용을 추가로 읽고 수정 판단을 이어가는 과정**이다. 현재 `propose_bundle_local`은 변경 블록을 요구하고, 블록이 없으면 형식 재질문 후에도 없을 때 ToolError로 거부한다. characters의 근거 요청도 이 경로에서는 “블록 없음”으로 기록됐다.

### 구현 가이드

- 모델 응답/오케스트레이터 상태를 `patch`, `needs_context`, `blocked`, `no_change`로 구분하는 계약을 만든다. 임의 설명문을 성공 수정으로 받아들이거나 모든 거부를 근거 요청으로 해석하지 않는다.
- 첫 도입은 읽기 도구만: 프로젝트 내부 문자열 검색, 파일 구간 읽기, 함수/메서드 정의·호출 위치 확인. 기존 파일 읽기·민감 경로·심볼릭 링크 제한을 재사용한다.
- 파일은 실제 작업 폴더 대신 **지금 수정 중인 격리 복사본**에서 읽는다. 경로·줄 범위·내용 지문·요청 이유를 기록한다.
- 한 수정 회차에서 추가 읽기 라운드는 작은 고정 상한부터 시작하고, 시간·모델 호출·입출력 예산에 포함한다. 예시 개발 시작값 2회는 제안일 뿐 최적 실측값이 아니다.
- 읽기 허용과 쓰기 허용을 분리한다. `web.py`를 참고로 읽었다고 자동 수정 대상에 추가하지 않는다. 범위 밖 수정이 필요하면 요청·중단 상태로 남긴다.
- 기존 진단 근거를 먼저 주고 누락이 확인됐을 때만 탐색한다. 진단 비교 완료 결과가 나오기 전에는 기본 활성화 여부를 확정하지 않는다.

수정 후보 위치: `jarvis/core.py`의 `propose_bundle_local` 앞뒤 생성 계약, `jarvis/developer.py`의 수정 회차 처리. 현재 웹 검색 도구 계약을 그대로 코딩 명령 실행에 확대하지 않는다.

수용 기준: 후보 복사본의 최신 내용 읽기, 경로 제한·취소·총예산 준수, 읽기만으로 쓰기 권한 확대 금지, 읽은 API를 사용하는 작은 결정적 CPU 대역 검사. 효과는 현재 평가 이후 **같은 실패 과제에서 기존 단발 진단 대비 추가 해결·모델 호출·시간**으로 비교한다.

## 3순위 — 테스트가 통과한 우회 수정과 일부 복원을 잡는 계약 검사

과거 `core 1679`는 작은 한도 분기를 삭제하고 호출부에서 다시 잘라 엄격 검사를 통과했다. gpumodel 사례는 환경변수 읽기를 빠뜨려도 통과했다. 이는 전체 회귀 검사로도 검사하지 않은 동작까지 보장할 수 없다는 증거다.

- `_truncate_text`의 한도 0·작은 양수·경계 80 전후·긴/짧은 입력에 대해 **현행 명세를 먼저 확정**하고 반환 길이·보존 내용 검사를 만든다. 모델이 바꾼 결과를 정답으로 삼지 않는다.
- 설정 기능에는 파일 설정뿐 아니라 환경변수 입력·우선순위·기본값 경로를 포함한다.
- 역사 과제의 기대 동작·삭제된 기능·검사 범위를 manifest에 기록한다. 원본과 한 글자도 같아야 한다는 검사는 피하고 동등한 올바른 구현을 허용한다.
- 추가 검사는 다음 평가 버전에서 고정한다. 과거 4/5·9/11을 강화된 새 검사까지 통과한 결과로 소급 표현하지 않는다.

우선 평가 품질과 다음 학습 자료의 정확도를 높이는 작업이다. 새 검사 때문에 점수가 일시적으로 낮아져도 그것은 악화와 구분해야 한다. 생성 테스트를 여러 후보 선택에 사용하는 CodeT는 이후 단계이며, 생성 검사가 명세·기존 검사보다 우선하면 안 된다.

## 4순위 — 실패 유형에 맞춘 문맥·수정 예산 배분

48K 조합의 전체 시간은 96분→189분으로 늘었다. 처리 속도 자체보다 잘못된 회차·중복 문맥·불필요한 생성 비용을 줄일 여지가 있다.

- 실제 입력/생각/출력 토큰, provider 호출 수, 형식 재질문, 검색·검사·trim 시간을 회차별 기록한다. 현재 `rounds`는 테스트 횟수이므로 모델 호출 수와 같지 않다.
- 짧은 파일·정확한 실패 위치가 있는 작업은 필요한 정의·호출부·검사 기대값 중심의 입력을 개발 비교한다. 근거 부족한 큰 작업을 무조건 작은 문맥으로 자르지 않는다.
- 모르는 API·근거 요청은 탐색으로, 명세 추론 실패는 독립 풀이로, 형식 문제는 작은 변경 단위/출력 계약 보완으로 처리한다. 모든 실패에 같은 재질문을 반복하지 않는다.
- 독립 풀이 설정·동적 출력 예산·유일 SEARCH 보완은 이미 있으므로 우선 현재 로그에서 효과를 확인한다. 전체 파일 재작성·무조건 3회 독립 풀이·모든 과제 48K 이상을 기본으로 켜지 않는다.

성과 기준: 동일 과제의 엄격 성공·의미상 올바른 수정 유지, 성공당 시간·추가 호출 감소. 14B 자동 라우팅은 같은 코딩 과제 품질 근거가 부족해 이번 첫 구현 대상으로 삼지 않는다.

## 바로 이어받을 수 있는 작업 범위

**현재 안전하게 가능한 작업:** 최신 결과를 읽기 복사하고 과제·실패 유형 비교, 다음 과제 계약/manifest 초안, 위 1·2순위의 모델 없는 상태·인터페이스 설계, 필요한 계약 검사 목록 작성. 이번 문서는 여기까지 수행했다.

**현재 대기:** 진단 켬 평가의 최종 수집. 실행 중 소스·테스트·설정·평가 스크립트·얼린 복사본 수정, Ollama/GPU 호출, 앱 재시작은 하지 않는다. 사용자 요청/기존 인계에서 취소된 120B 품질 평가를 이번 재검토를 이유로 재개하지 않는다.
