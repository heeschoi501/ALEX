# 코딩 에이전트를 Sonnet 5 수준으로 — 조사와 계획 (2026-10-03, claude)

사용자(2026-10-03): "지금 극대화해야 하는 건 코딩에이전트 … 능력을 끌어올릴 수 있는 방안을 찾아줘. 적어도 sonnet 5.0 수준으로".

## 1. 결론 먼저

- **모델은 이미 Sonnet 5 근처에 있다(발표 수치 기준).** 이 PC에 설치된 `qwen3.8-flash-next:125b`(125B, 활성 6B)는 SWE-bench Pro 62.5로, Claude Sonnet 5의 63.2와 거의 같다. 제3자 지수인 AA Coding Index는 73.0으로 Sonnet 5의 71.5보다 높다.
- **병목은 하네스다.** 위 점수는 Claude Code·mini-SWE-agent 하네스와 256K 문맥에서 나왔다. ALEX 코딩 에이전트는 다음 조건으로 돈다.
  - 문맥 16K
  - 고칠 파일만 보여 준다. 큰 파일은 발췌만 보여 준다.
  - 모델이 직접 코드를 찾거나 다른 파일을 열 수 없다.
  - 한 번에 수정안 1개를 내고, 최대 3번까지 다시 고친다.
  - 기본 모델은 27b다.
- **같은 모델이라도 하네스만 바꿔서 성공률이 10~24%p 달라진다**(Claw-SWE-Bench, 아래 출처).
- **할 일의 순서.** 무엇이 효과를 냈는지 가를 수 있게, 한 번에 하나씩 바꾸고 같은 과제로 잰다.
  1. 측정 기준을 만든다.
  2. 125B로 바꾼다.
  3. 문맥을 늘린다.
  4. 탐색 도구를 준다.
  5. 여러 번 풀게 해서 테스트로 고른다.
- **솔직한 한계.** 정답률은 Sonnet 5에 가까워질 수 있다. 하지만 이 PC에서는 다음 셋이 Sonnet 5에 미치지 못한다.
  - 속도: 과제당 수십 분.
  - 범용성: 큰 기능 설계, 여러 파일 리팩터링.
  - 안정성: 120GB 모델이 RAM+VRAM 109GB보다 크다. 9/26에 CUDA 오류가 한 번 났다.

## 4. 방안 — 근거와 기대 효과

### ① 측정 기준부터: "ALEX 역사 과제"(SWE-bench 방식)

- SWE-bench는 실제 이슈를 고친 PR의 테스트를 합격 기준으로 쓴다(Jimenez et al. 2024). ALEX도 같은 재료가 있다. 고치기 전 백업(`logs/*backup*`)과 그 수정 때 추가된 테스트다.
  - 예: Codex 10/03 `developer.py` 거짓 통과 수정과 테스트 4건
  - 예: claude 10/03 `video_plan`·`Wan14VideoTests` 6건
- 과제 하나 = (고치기 전 파일들, 고친 뒤의 테스트, 목표 문장). 새 테스트가 고치기 전 코드에서 실패해야 과제로 쓴다.
- **"Sonnet 수준"의 정의:** Claude·Codex가 실제로 풀어낸 ALEX 과제를 로컬 에이전트가 사람 도움 없이 몇 %나 푸는가.
  - 선택: 10개 정도는 Claude Code를 사람 없이 돌려 기준선을 잰다(사용량이 든다).
- 변이 세트(쉬움 16·어려움 11)는 회귀 확인용으로 둔다.

### ② 125B로 바꾸기 (이미 설치됨, 비용 0)

- 같은 하네스로 hard 11 + test 16을 잰다. 27b 결과와 과제별로 짝지어 비교한다. 이렇게 하면 모델 효과만 따로 볼 수 있다.
- 조건(MODEL_CHOICE와 같음):
  - FA 끔, 기본 클럭
  - 83°C나 CUDA 오류가 나면 중단
  - ComfyUI와 대화는 쓰지 않는다
  - 샘플링은 모델 카드 권장값(생각 모드 temp 1.0, top_p 0.95, top_k 20)

### ③ 문맥 16K → 64K~128K

- 발표 점수의 조건은 256K였다. 문맥을 늘리면 `core.py`(약 3만 토큰)를 발췌 없이 통째로 보여 줄 수 있다. 발췌 밖 API를 몰라서 실패하던 유형을 직접 겨냥한다.
- 속도, 메모리, 첫 토큰까지의 시간을 문맥 길이별로 잰다. 하네스가 대화를 앞에서부터 그대로 이어 붙이면 Ollama가 앞부분 계산을 재사용한다.

### ④ 탐색 도구가 있는 에이전트 루프 (가장 큰 레버로 예상)

- 모델이 스스로 아래 도구를 부르며 여러 차례 진행한다. 모든 동작은 격리 복사본 안에서만 한다.
  - 찾기: 파일 안 문자열 검색
  - 파일 범위 보기
  - 목록 보기
  - 합격 테스트·지정 테스트 실행
  - 기존 SEARCH/REPLACE 수정
- 근거:
  - mini-SWE-agent는 약 100줄짜리 루프로 SWE-bench Verified 74% 이상을 낸다(강한 모델 기준). Flash Next의 DeepSWE 58.7도 이 하네스에서 나왔다.
  - SWE-agent는 도구 설계(ACI)가 성능을 좌우한다고 보고했다.
  - 같은 모델에서 하네스 차이가 최대 24.3%p였다(Claw-SWE-Bench).
- 안전선은 그대로다.
  - 셸 전체 대신 허용한 도구만 쓴다(Windows·안전).
  - tests/는 고칠 수 없다.
  - 실제 파일은 사용자 승인으로만 바뀐다.
- 대화 기록은 한 줄로 이어 붙인다(mini-SWE-agent 방식). 그래야 앞부분 계산을 재사용해 빠르다.

### ⑤ 여러 번 풀고 테스트로 고르기 (재시도보다 재표본)

- Large Language Monkeys: 같은 모델의 SWE-bench Lite가 표본 1개일 때 15.9%에서 250개일 때 56%로 올랐다. 코딩은 테스트라는 자동 검증기가 있어서 표본을 늘린 만큼 오른다.
- Self-Repair 연구(Olausson et al., ICLR 2024): 같은 계산량이면 같은 답을 고쳐 나가는 것보다 새로 여러 번 푸는 편이 대개 낫다. 고치기의 효과는 자기 오류를 알아보는 능력에 막힌다.
- 그래서 지금의 "1개 × 3번 고치기" 예산 일부를 "N개 독립 풀이 → 합격 테스트·전체 검사를 통과한 것 중 변경이 가장 작은 것"으로 옮긴다.
  - 시작은 N=3이다. 밤사이 돌리는 자기 개선 작업에 맞는다.

### ⑥ 스스로 성장 (뒤 단계)

- 테스트로 검증된 풀이 기록을 학습용 형식으로 모은다(`dev-outcomes.jsonl` 확장). SWE-smith, SWE-Gym은 검증된 풀이 기록으로 미세조정해 공개 모델 점수를 크게 올렸다.
  - 단, 이 PC(16GB)에서는 27B·125B 미세조정이 어렵다. 장비가 바뀔 때를 위해 데이터만 먼저 쌓는다.
- 목표 문장만 있고 테스트가 없는 일(새 기능)을 위해, 에이전트가 먼저 재현 테스트를 쓰게 한다(Agentless의 재현 테스트).
  - 테스트는 합격 기준이므로 **사용자 승인 뒤에만** 쓴다.
- 교훈(ADR-070)은 ④ 다음에 다시 잰다. 지금은 효과가 없었다.

## 6. 하드웨어와의 관계

- 125B Q4 모델은 120GB다. RAM 93GB + VRAM 16GB = 109GB보다 커서 일부를 디스크에서 읽는다. 9/26 측정은 GPU 12GB + RAM 100.5GB에 22.6 tok/s였다.
- 긴 문맥과 N개 풀이에서 이 부분이 병목이 되면, 맥보다 싼 RAM 증설(192GB)이 첫 후보다(MODEL_CHOICE_20260930). 단계 1~2 측정을 보고 판단한다.
