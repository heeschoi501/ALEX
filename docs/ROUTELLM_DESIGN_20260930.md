# ALEX 과제별 14B/27B 추천 설계 — 2026-09-30

상태: 설계만. 기본 모델 gpt-oss:120b·하드웨어/모델 설정은 유지한다. 모델 다운로드·Ollama 실행·서버 재시작 없음.

## 출처와 목표

[RouteLLM 공식 저장소](https://github.com/lm-sys/RouteLLM), [논문](https://arxiv.org/abs/2406.18665)은 과제별 강한/저렴한 모델의 품질·비용 절충을 다룬다. 공식 문서의 mf/sw_ranking은 임베딩에 OpenAI API가 필요하므로 그대로 넣으면 로컬 전용 경계에 맞지 않는다. 초기 구현 후보는 프레임워크 설치 없이 ALEX 자료에 기반한 규칙 추천기다. 학습된 RouteLLM을 이미 구현했다고 표현하지 않는다.

목표는 모든 요청을 빠른 모델로 보내는 것이 아니라 **과제 성공까지의 시간과 재작업 비용**을 줄이는 것이다. 첫 단계는 추천·근거 표시만 하며 자동 모델 변경은 범위 밖이다.

## 실측 근거와 적용 한계

출처: [PERFORMANCE 29·30](../PERFORMANCE.md), [평가 스냅샷](CODEX_EVAL_SNAPSHOT_20260930.md).

| 조건 | 확인한 값 | 추천에 사용할 때의 제한 |
|---|---|---|
| qwen3.8:27b f16/16K/54층 | 생성 19.4/34.8/17.3 tok/s, 긴 입력 1117 tok/s, CPU 58% | 54층은 16K에서 확인. 다른 모델/문맥에 복사하지 않음 |
| qwen3:14b q8_0 16/32/64K | 생성 77/79/79 tok/s, CPU 13~16%, GPU 100% 배치 | 27B와 KV가 다름. 속도를 코딩 품질로 환산하지 않음 |
| qwen3:14b f16/64K | 생성 32.6 tok/s, CPU 53% | q8_0의 속도·CPU 장점이 모든 설정에서 유지되는 것은 아님 |
| 27B 변이 test16 | strict 15/16, 원본 동일 11 | 쉬운 과제. 14B 동일 평가 결과 없음 |
| 오답 바로잡기 | 14B 0/3, 27B 3/3 | 특정 대화·작은 표본. 전체 작업 품질로 일반화하지 않음 |

27B 자동 배치와 비교한 14B의 5~6배 표현을 54층 최적화·모든 과제에 반복 적용하지 않는다. CPU 사용률은 소음이나 전력의 직접 측정치가 아니며 Mac Studio 성능/구매 효과로 외삽하지 않는다.

기준선의 15/16은 결과 행 단위이며 고유 ID는 15개다(과거 변이 ID 충돌). 모델 간 과제별 비교 전에 입력 변이 해시로 대응을 확인해야 한다.

## ALEX 구조에 들어갈 위치

1. `router.route_request`의 기존 목적지·도구·클라우드 경계를 먼저 결정한다. 이 추천기는 권한이나 도구 종류를 바꾸지 않는다.
2. 로컬 목적지이면 별도 `LocalModelAdvisor`가 추천을 반환한다. 새 모듈 후보는 `jarvis/model_advisor.py`이나 이번에는 생성하지 않는다.
3. `/dev-auto`는 일반 채팅 라우터를 거치지 않으므로 DeveloperMode의 생성 진입점에서도 같은 추천기를 사용한다. 코드 편집의 `_generate_local_edit` 로컬 전용 규칙은 유지한다.
4. 초기에는 추천을 표시/기록만 한다. 사용자가 특정 작업에 추천을 선택하면 그 작업에 한해 별도 provider/options를 사용한다. 공용 provider.model을 변경했다 되돌리는 방식은 동시 작업과 충돌할 수 있어 피한다.
5. 명시적 모델 선택은 추천보다 우선한다. 제안 모델이 설치되지 않았거나 설정 호환성이 불명확하면 unavailable/unknown을 반환하며 자동 다운로드하지 않는다.

## 데이터 계약 제안

`AdviceInput`: task_kind, local_destination, context_chars, file_count, largest_file_bytes, acceptance_tests_present, recent_failure_types, preferred_latency, explicit_model, available_models, runtime_profile_id.

`ModelAdvice`: recommended_model 또는 null, reason_codes, evidence_ids, evidence_level(measured/extrapolated/unknown), constraints, selected_by_user, policy_version. 입력은 기존 메타데이터에서 얻고 추천을 위해 추가 LLM 호출을 하지 않는다.

`AdviceOutcome`: advice_id, actual_model, source/task/config 지문, acceptance/suite 결과, cold_start/load/first_token/total_seconds, generation tokens, retries, user_override. 자연어 요약·변환의 품질은 사용자가 사전 정의한 점검표로 평가하고 테스트가 없다고 자동 성공 처리하지 않는다.

## 초기 추천 규칙 — 검증 전 가설

| 상황 | 추천 후보 | 근거/제한 |
|---|---|---|
| 짧은 형식 변환·발췌·단순 요약, 속도 우선 | 14B 시험 추천 | 처리 속도 근거는 있으나 해당 과제 품질은 별도 검증 필요 |
| 회귀 수정·여러 파일·반복 실패 | 27B 시험 추천 | 코딩 기준선 존재. 모든 복잡한 과제 성공 보장 아님 |
| 과거 오답이 쌓인 대화의 바로잡기 | 27B 추천 후보 | replay 3/3 대 0/3의 제한된 근거 |
| 16K 초과 또는 메모리 설정 미검증 | 유보/조건부 추천 | 27B 54층을 그대로 강제하지 않음 |
| 사용자가 모델 명시 | 명시 모델 유지 | 추천은 참고 정보만 |
| GPU 실험 중·활성 작업과 충돌 | 실행 전환 유보 | 추천 때문에 unload/적재/재시작하지 않음 |

14B의 코딩 품질은 현재 동일 과제 기준 미검증이므로, 코드 작업을 자동 배정하거나 자동 14B→27B 계단식 실행을 켜지 않는다. “추천 근거 부족”은 정상 결과다.

## 성능·운영 제약

- KV 형식은 Ollama 서버 설정이다. 한 서버에서 요청마다 14B=q8_0, 27B=f16으로 임의 전환한다고 설계하지 않는다. 비교에는 현재 같은 서버 설정에서의 측정이 필요하다.
- 모델별 GPU 층·문맥 설정은 모델+runtime profile에 연결한다. 27B의 54층을 gpt-oss:120b나 다른 문맥에 재사용하지 않는다.
- 모델이 이미 올라간 상황과 교체가 필요한 상황을 구분한다. 추천 시스템 때문에 `/unload`를 자동 호출하지 않는다.
- 비용은 `입력 처리 + 모델 적재/교체 + 생성 + 검사 + 실패 후 재시도`다. 14B 실패 뒤 27B 재시도의 기대비용이 바로 27B보다 클 수 있다. 현재 데이터로 실패 확률을 임의 추정하지 않는다.
- 설정 파일 자동 변경·클라우드 fallback 확대는 범위 밖이다. 기능을 끄면 기존 경로와 실제 모델 선택이 그대로 유지되어야 한다.

## 검증 계획

1. 고정 snapshot의 같은 과제를 14B/27B가 각각 풀게 하는 후속 평가를 계획한다. 현재 실험 중에는 시작하지 않는다. 모델·양자화/KV·문맥·층·think·온도·하드웨어·소스/과제 지문을 manifest로 남긴다.
2. 과제 유형별 개발/검증/최종 평가를 함수·유사 과제 단위로 분리한다. 같은 변이의 다른 형태가 양쪽에 들어가지 않도록 한다.
3. 추천 기록 모드로 추천과 기존 실제 모델 선택을 함께 남긴다. 정책 조정은 개발/검증셋에서만 하고 최종 평가 전에 고정한다.
4. 비교: 고정 14B / 고정 27B / 추천 정책. 사용자 기본 120B의 변경 근거로 쓰려면 동일 과제의 120B 비교가 별도로 필요하다.
5. 지표: 과제별 strict 성공, 회귀, 근거 없는 추천, 사용자 재선택, total 시간 중앙값·상위 지연, 모델 교체·재시도 비용. 작은 표본은 원시 건수와 과제 ID를 함께 제시한다.
6. 충분한 성공·선호 쌍이 쌓인 뒤에만 학습 라우터를 고려한다. 로컬 임베딩/분류기와 ALEX 데이터로 검증하고 API 전송 여부를 명시한다. 공개 사전학습 임계값을 그대로 가져오지 않는다.

## 구현 전 필요한 결론

모델별 동일 조건 품질 자료, 사용자 허용 지연, 추천 표시 방식, runtime profile 정의가 필요하다. 현재 단계의 구현 후보는 가벼운 추천 기록과 근거 표시이며 자동 전환은 후속 결정이다.
